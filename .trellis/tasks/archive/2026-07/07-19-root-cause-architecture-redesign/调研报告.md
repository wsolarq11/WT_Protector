# 根源架构调研最终报告

> 调研日期：2026-07-19 | 调研项目：6 个外部 + 社区资源

## 一、同类项目架构

### Flow Launcher
插件+查询管道模式。每个 Plugin 实现 IPlugin 接口并行查询。ViewModel 按功能域分割（Main/Settings/PluginStore），无神类。用 MS.DI。

### RoslynPad (Avalonia)
无神类 ViewModel，每个屏幕独立 VM。多项目解耦。DI 串联非主 VM 持有。

### Prism.Avalonia
Module（独立 DI 注册）、Region（区域导航）、IDialogAware（对话框 VM）、EventAggregator（Pub/Sub）。

## 三、架构反模式与方案

### 神类 ViewModel → Feature Module
Partial Class（当前）→ Extract Class → Feature VM → 消息总线 → Shell 瘦身

### 状态投影漂移 → NotifyPropertyChangedFor
手动 7 行 OnPropertyChanged → 注解自动发射

### 异常处理 → ExceptionBoundary.RunAsync
重复 21+ 次的 catch-log-return → 统一辅助类

## 四、根因 × 方案对照

| 根因 | 方案 | 参考来源 |
|------|------|---------|
| 神类 VM 16 partials | Feature Module 拆分 | Flow Launcher, RoslynPad |
| 异常 21+ 重复 | ExceptionBoundary | .NET 最佳实践 |
| 投影手动维护 | NotifyPropertyChangedFor | CommunityToolkit |
| AOT 无验证 | 注册测试 | MS STJ 文档 |
| 生命周期泄漏 | 消息总线 + Dispose | CommunityToolkit |

## 五、核心结论

最大单一问题：**功能域边界 ≠ 封装边界** — 16 partials 按域分割代码但编译时仍是同一个类。解决路径不是重写，是提取式重构，利用已有的 `IEntryService` / `IDialogService` 接口作为边界基础设施。
